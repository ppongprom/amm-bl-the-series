## 0. แหล่งความจริง (Source of Truth) — เรียงลำดับความน่าเชื่อถือ

เวลาสงสัยว่าตัวละครควรมีลักษณะ/prop แบบไหน ให้ตรวจตามลำดับนี้ **ภาพสำคัญกว่าตัวหนังสือเสมอ**
เพราะภาพคือสิ่งที่ Flow ใช้เป็น Ingredient จริง ไม่ใช่ text spec:

1. **ภาพ reference จริงใน `references/*.jpeg`** — ภาพ turnaround sheet ที่ generate ไว้แล้วและ
   ใช้เป็น Ingredient (`@ชื่อ_v1`) จริงในระบบ ถ้าภาพกับ text spec ขัดกัน **ให้ยึดภาพเป็นหลัก**
   เพราะนี่คือสิ่งที่ Flow มองเห็นจริงตอน generate ไม่ใช่ text
2. **`character-visual-prompts.md`** (ต้นฉบับที่ใช้ generate ภาพ reference ข้างต้น) — ใช้เทียบ
   เพื่อเข้าใจ "เจตนา" เบื้องหลัง prop/ลักษณะนั้นๆ (ทำไมถึงออกแบบมาแบบนี้)
3. **`docs/continuity-bible.md`** — กำหนด timeline ว่าแต่ละตอนเกิดวันไหน (ตอนไหนวันเดียวกัน ตอนไหน
   คนละวัน), ข้อเท็จจริงที่ตั้งไว้แล้วของแต่ละตัวละคร/เหตุการณ์, และภาคผนวก Identity Prop vs
   Outfit — **ต้องเช็คก่อนเขียนทุกตอนว่าตอนนี้อยู่วันเดียวกับตอนก่อนหน้าหรือคนละวัน** เพราะกำหนด
   scope ว่า outfit ต้องเหมือนหรือต่างจากตอนก่อนหน้า (ดูข้อ 1B) — **`character-visual-prompts.md`
   และ `docs/continuity-bible.md` ทั้งคู่ย้ายเข้า `docs/` ของ repo นี้เป็นไฟล์ถาวรแล้ว (ยืนยันจริง
   20 ก.ย. 2569 ระหว่างเตรียมเขียน ep06 — ก่อนหน้านั้น `character-visual-prompts.md` ประกาศว่าย้าย
   แล้วแต่ตัวไฟล์จริงยังค้างอยู่ใน scratchpad ชั่วคราวเท่านั้น พบและแก้โดย Mint ระหว่างตรวจ signature
   prop ของแทน) ไม่ต้องพึ่ง scratchpad อีก**
4. **ไฟล์ shorts-prompt ของตอนก่อนหน้า** (ถ้ามี) — เพื่อเช็ค continuity ข้ามตอน (เช่น outfit ของ
   ตอนก่อนหน้าใช้สีอะไรไปแล้ว จะได้ไม่เลือกซ้ำโดยไม่ตั้งใจถ้าเป็นคนละวัน)

**ห้ามเขียน prompt จากความจำ** — ก่อนเขียนทุกครั้งต้องเปิดทั้งภาพ reference, text spec, และ
continuity bible ของทุกตัวละครที่จะปรากฏใน scene นั้นๆ มาดูจริง (นี่คือจุดที่ ep07 พลาด — Bank
ยืนยันว่าไฟล์ไม่มีร่องรอยว่าเทียบกับ spec ระหว่างเขียนเลย)

## 1. Identity Prop Lock (ตลอดเรื่อง) vs Outfit of the Day Lock (รายตอน)

**หลักการร่วม (ทำไมต้องมีข้อนี้):** Google Flow generate **แต่ละ scene แยกจากกัน ไม่มี memory
ข้าม prompt เลย** — ถ้าประโยคบรรยายกว้างๆ ไม่ระบุรายละเอียด (เช่น "each wearing their own
headphones" หรือ "wearing his usual outfit") Flow จะ**เดาเอาเองใหม่ทุกครั้งที่ generate** และเดา
ไม่ตรงกันในแต่ละ scene แน่นอน — นี่คือต้นตอที่แท้จริงของปัญหาหูฟังเปลี่ยนชนิดใน ep07 (ยืนยันโดย
คุณอั้ม)

**⚠️ ต้องแยก 2 ระดับให้ชัด ห้ามปนกัน (คำพูดต้นฉบับจากคุณอั้ม 20 ก.ย. 2569):**

> "รายละเอียดต้องลงทุกอย่าง ลักษณะหน้าตา ประเภทของอุปกรณ์ที่ใช้ ถ้าให้เป็นเอกลักษณ์ของตัวละคร
> จำเป็นต้องเหมือนกันทุก ep ตลอดทั้งเรื่อง ส่วนเสื้อผ้าสามารถเปลี่ยนได้ ถ้าเป็นคนละวัน ไม่ต่อเนื่อง
> จาก ep ก่อนหน้านี้"

| | ระดับ 1: Identity Prop | ระดับ 2: Outfit |
|---|---|---|
| **ครอบคลุม** | ลักษณะหน้าตา (โครงหน้า ทรงผม สีผม ตา ผิว ส่วนสูง รูปร่าง) + อุปกรณ์/prop เอกลักษณ์ประจำตัว (เช่น หูฟัง แว่น) | เสื้อผ้าที่ใส่ (เสื้อ กางเกง รองเท้า) |
| **Scope ที่ต้องเหมือนกัน** | **ตลอดทั้งเรื่อง ทุก ep** ห้าม variation ข้าม ep เด็ดขาด | **ภายใน ep เดียวกันเท่านั้น** (ทุก scene ของตอนนั้น) |
| **ข้าม ep** | ต้องเหมือนเป๊ะทุกตอน | เปลี่ยนได้/ควรเปลี่ยนถ้าคนละวัน (ดู `docs/continuity-bible.md`) |
| **อ้างอิง** | `character-visual-prompts.md` + `references/*.jpeg` เป็นค่าตายตัว | `character-visual-prompts.md` เป็นฐาน + ปรับสี/แบบตามวันได้ |
| **รายละเอียดเต็ม** | หัวข้อ 1A ด้านล่าง | หัวข้อ 1B ด้านล่าง |

### 1A. Identity Prop Lock (ตลอดเรื่อง) — ลักษณะหน้าตา + signature prop

ตัวละครบางตัวมี **signature prop** ที่ตั้งใจออกแบบให้ต่างจากคนอื่นเพื่อสื่อความหมาย (เช่น ดิว =
over-ear headphones เก่าสายลุ่ย vs นนท์ = in-ear ราคาประหยัด — สื่อสถานะ/รุ่น/บุคลิกที่ต่างกัน
ตามที่ Mint ยืนยัน) รวมถึงลักษณะหน้าตาทั้งหมด — สิ่งเหล่านี้ **ห้ามเปลี่ยนกลาง scene หรือข้าม ep
โดยไม่มีเหตุผลในเนื้อเรื่องเด็ดขาด** (ดูรายละเอียดที่ยืนยันแล้วของดิว/นนท์ใน
`docs/continuity-bible.md` ภาคผนวก)

### กฎ
- **ก่อนเขียน prompt ของตอนไหน ให้ copy บรรทัด spec ของลักษณะหน้าตา + signature prop ทุกตัวละคร
  ที่ปรากฏ มาแปะเป็น checklist บนสุดของไฟล์ตอนนั้น** (ดูตัวอย่างหัวข้อ "Prop State Table" ด้านล่าง)
  — เหมือนกันทุก ep ไม่ต้องเช็คว่าตอนก่อนหน้าเขียนว่าอะไร เพราะค่าตายตัวอยู่แล้ว
- **ห้ามใช้คำกลางๆ แทนชื่อเฉพาะ** — เขียน "over-ear headphones" หรือ "worn over-ear headphones
  with frayed cable" เสมอ ห้ามใช้ "headphones"/"earbud" ลอยๆ แทนกันไปมา (คำกลางๆ คือจุดที่ ep07
  เริ่มหลุด — Bank อ้างบรรทัด 78-81, 100-101)
- **ถ้า scene ต้องการให้ signature prop 2 ชิ้นมา "ปฏิสัมพันธ์กัน" (แบ่ง/แลก/ยืม) ต้องตรวจก่อนว่า
  prop สองชิ้นนั้นทำปฏิสัมพันธ์แบบที่ต้องการได้จริงทางกายภาพหรือไม่** ถ้าไม่ได้ (คนละชนิดกัน เช่น
  over-ear vs in-ear ถอดแบ่งข้างกันไม่ได้) **ห้ามเปลี่ยนชนิด prop เพื่อความสะดวกของ scene** —
  ให้ออกแบบ action ใหม่ที่ทำให้ prop เดิมทำงานร่วมกันได้แทน (ดูตัวอย่างจริงที่แก้ไว้ใน ep07.md
  Scene 4 — นนท์ถอด in-ear ข้างขวายื่นให้ดิวใส่ชั่วคราว ส่วนดิวถอด over-ear ของตัวเองลงมาคล้องคอ
  ไม่ใช่เปลี่ยนดิวให้กลายเป็นคนใส่ earbud)
- **ทุกครั้งที่ prop ถูกถอด/สวม/ส่งต่อ ต้องเขียน action ของทั้งสองฝั่งให้ครบ** (ถอดออกจากใคร ข้าง
  ไหน ใส่เข้าที่ใคร ข้างไหน) ห้ามระบุแค่ฝั่งเดียวแล้วปล่อยอีกฝั่งให้ Flow เดา

### Prop State Table (ตัวอย่าง — แปะไว้บนสุดของทุกไฟล์ shorts-prompt — ใช้ค่าเดียวกันทุก ep)

### 1B. Outfit of the Day Lock (รายตอน) — เสื้อผ้า/สี/ทรง ล็อก "ภายในตอน" ไม่ใช่ "ตลอดทั้งเรื่อง"

**ข้อกำหนดจากคุณอั้ม (20 ก.ย. 2569, ชี้แจงเพิ่ม):** ไม่ใช่แค่ prop ชิ้นเล็กอย่างหูฟังที่ต้องล็อก
**เสื้อผ้าทั้งชุดของทุกตัวละครในทุก scene ก็ต้องระบุรายละเอียดเต็ม (ทรง/สี/เนื้อผ้า) ซ้ำทุกครั้ง**
ด้วยเหตุผลเดียวกันเป๊ะ — Flow ไม่มี memory ข้าม prompt ถ้าเขียนแค่ "wearing his usual outfit" หรือ
ไม่พูดถึงเสื้อผ้าเลย Flow จะเดาสี/ทรงใหม่ทุก scene และมีโอกาสสูงที่จะเดาไม่ตรงกัน

**⚠️ ขอบเขตของ "consistency" — สำคัญ อย่าตีความผิด:**
- **ข้าม ep ต่างกันได้/ควรต่างกัน** — แต่ละตอนคือคนละวันตาม timeline ที่ `docs/continuity-bible.md`
  กำหนดไว้ (เช่น ep04-05 คือวันศุกร์สัปดาห์ 2, ep06 คือวันอังคารสัปดาห์ 3, ep07 คือวันพฤหัสบดี
  สัปดาห์ 3) การใส่ชุดเดิมทุกวันจะขัดกับ "กฎสมจริง 100%" ที่ bible ตั้งไว้ (บรรทัด 2) — ใส่ชุดต่างกัน
  ข้าม ep คือ **signal ที่ถูกต้องให้คนดูรู้ว่าเวลาเปลี่ยนแล้ว ไม่ใช่บั๊ก**
- **ภายใน ep เดียวกัน (ทุก scene ของตอนนั้น) ต้องเป็น outfit ชุดเดียวกันเป๊ะ** — เพราะทุก scene ใน
  ตอนเดียวกันคือวันเดียวกัน ช่วงเวลาต่อเนื่องกัน (เช่น ep07 ทั้ง 7 scene คือคืน OT คืนแรกของดิว-นนท์
  คืนเดียวกันทั้งหมด — ดู `docs/continuity-bible.md` บรรทัด "ตอน 7: วันพฤหัสบดี สัปดาห์ 3 (ค่ำ)")

### กฎ
- **ทุกตอนต้องกำหนด "Outfit of the Day" ต่อตัวละครที่ปรากฏในตอนนั้น แปะไว้ตอนต้นไฟล์ 1 ครั้ง**
  (อ้างอิงจาก `character-visual-prompts.md` เป็นฐาน + ปรับสี/แบบให้ต่างจากตอนก่อนหน้าได้ถ้าจำเป็น
  เพื่อสื่อว่าเป็นคนละวัน — เช็คตอนก่อนหน้าว่าใช้ชุดอะไรไปแล้วก่อนเลือกชุดใหม่ ไม่ให้ซ้ำเป๊ะข้ามวัน
  โดยไม่ตั้งใจ)
- **ทุก scene prompt ในตอนนั้นต้อง copy คำอธิบาย Outfit of the Day ชุดนั้นซ้ำคำต่อคำ** ไม่เปลี่ยน
  แม้แต่รายละเอียดเล็ก (สี/ทรง/เนื้อผ้า) — อ้างอิงตรงจาก spec/ภาพ reference ไม่ใช่คำกลางๆ เช่น
  ดิว = "dark charcoal-grey oversized t-shirt with a subtle grey logo print, grey tailored
  trousers, white sneakers" ไม่ใช่แค่ "his usual outfit" หรือ "casual clothes"
- **ห้ามสมมติว่า Flow "จำ" เสื้อผ้าจาก scene ก่อนหน้าได้** — ต้องเขียนซ้ำคำต่อคำทุก scene แม้จะ
  เป็นตอนเดียวกันต่อเนื่องกันก็ตาม (Flow generate แยก clip ไม่มี state ข้าม prompt)
- **ถ้าเนื้อเรื่องมีจุดเปลี่ยนเสื้อผ้าจริงภายในตอนเดียวกัน** (ถอดแจ็คเก็ต, ผูก/ถอดเนคไท ฯลฯ) ต้องมี
  action อธิบายจุดเปลี่ยนผ่านชัดเจนเหมือนกับ prop ในข้อ 1A ห้ามให้เสื้อผ้าเปลี่ยนโดยไม่มี action
  รองรับ

## 2. Blocking / ตำแหน่งนั่ง-ยืน ต้องตายตัว

**ปัญหาที่พบ:** ep07.md ไม่มี scene ไหนระบุ "ใครอยู่ซ้าย/ขวาของเฟรม" เลยทั้งไฟล์ ใช้แต่คำบรรยาย
เชิงสัมพันธ์ (adjacent, facing, beside, angled toward) ที่ตีความได้หลายแบบ และ Scene 2 ("facing
desks") ขัดกับ Scene 1/3/5/7 ("beside him"/"eye-level") ว่าโต๊ะเป็นหันหน้าเข้าหากันหรือเคียงข้างกัน

### กฎ
- **กำหนด layout คงที่ 1 ครั้งตอนต้นไฟล์** (เช่น "facing desks, ~1m gap, rolling chairs" หรือ
  "side-by-side desks, monitors facing same wall") แล้วทุก scene ต้องอ้างอิง layout เดียวกัน
  ห้ามสลับคำอธิบายไปมาข้าม scene
- **กำหนด camera-left / camera-right ของตัวละครหลักตั้งแต่ scene แรกที่ปรากฏร่วมกัน** แล้วล็อก
  ใช้คำเดิมซ้ำทุก scene ถัดไป เว้นแต่มีเหตุผลทางเรื่องให้สลับ (ต้องระบุเหตุผลในบทด้วย) — เขียน
  ควบคู่กับคำบรรยายเชิงสัมพันธ์เสมอ เช่น "Non on camera-left, Dew on camera-right, desks angled
  toward each other" ไม่ใช่แค่ "angled toward each other" เฉยๆ
- **Scene ที่ตั้งใจขยาย/ย้อนจาก scene ก่อนหน้า** (เช่น payoff ที่ขยายจาก hook) ต้องระบุ anchor
  ชัดว่า "same camera-left/right as Scene X" ไม่ใช่แค่บอกว่ามุมกล้องกว้าง/แคบกว่า
- **การเปลี่ยนระยะห่างทางกายภาพระหว่างตัวละคร** (เก้าอี้ขยับเข้าใกล้ ฯลฯ) ต้องมี action บรรทัด
  เฉพาะบอกว่า "ใครขยับ ขยับยังไง" ห้ามให้ mood/บรรยากาศบอกผลลัพธ์ลอยๆ โดยไม่มี action อธิบายสาเหตุ

### 2A. Setting/Furniture Lock — เฟอร์นิเจอร์เฉพาะสถานที่ต้องระบุใน Subject ซ้ำทุก scene

**พลาดจริง 20 ก.ย. 2569 (หลัง generate จริงรอบแรก):** คุณอั้ม generate Scene 5 ของ ep07.md
(ตอนนั้นยังไม่มีข้อนี้) ได้ภาพตัวละครนั่งเก้าอี้เปล่าๆ **ไม่เห็นโต๊ะทำงาน/จอคอมเลย** ทั้งที่ควรเป็น
ฉากนั่งทำงานที่โต๊ะ — ตรวจไฟล์แล้วพบว่า Scene 5 ตอนนั้นเขียนแค่ "leaning back... at his desk" ใน
Subject และ "both desks and monitors visible in frame" ใน Composition (บอกกว้างๆ ว่า "ให้เห็นใน
เฟรม" — เป็นคำสั่งบอกผลลัพธ์ ไม่ใช่คำบรรยายภาพที่ Flow generate ได้ตรง) ต่างจาก Scene 2 ที่เขียน
ชัดเจนว่า "sitting at angled facing desks about 1 meter apart" ตรงๆ ใน Subject — **เกิดจากช่องโหว่
เดียวกับ Prop/Outfit ที่เพิ่งแก้ไปแล้ว**: กฎ Blocking (ข้อ 2 ด้านบน) บังคับ camera-left/right ไว้แล้ว
แต่ไม่ได้บังคับให้ "โต๊ะทำงาน + เก้าอี้มีล้อ + จอคอม/คีย์บอร์ด" ต้องถูกเขียนลง **Subject** แบบเจาะจง
ทุก scene เหมือนกัน ปล่อยให้บาง scene เขียนกำกวมกว่า scene อื่น

### กฎ
- **ทุก scene ที่ตัวละครอยู่ในสถานที่ที่มีเฟอร์นิเจอร์/setting เฉพาะ (โต๊ะทำงาน, เก้าอี้ทำงาน,
  จอคอม, คีย์บอร์ด ฯลฯ) ต้องระบุเฟอร์นิเจอร์เหล่านั้นลงใน Subject description ตรงๆ ซ้ำทุก scene**
  ไม่ใช่แค่กล่าวถึงใน Composition แบบสั่งผลลัพธ์ลอยๆ ("desks visible in frame") — ใช้หลักการเดียว
  กับ Prop/Outfit Lock: **ห้ามสมมติว่า Flow จะ "จำ" หรือ "เดา" ได้เองจากบริบทกว้างๆ**
- **คำที่ใช้ต้องเจาะจง ไม่ใช่คำกลางๆ** — เขียน "sitting at his angled facing desk with his
  computer monitor and keyboard in frame" เสมอ ไม่ใช่แค่ "at his desk" หรือปล่อยให้ Composition
  พูดแทน
- **Scene ที่เป็น close-up/emotional beat** (เช่น hook ที่ครอปใกล้ ไม่ได้ตั้งใจให้เห็นโต๊ะเต็มๆ) ก็
  ยังต้องมี hint ของ furniture อย่างน้อย 1 จุดกันความกำกวม (เช่น "the edge of his computer monitor
  and keyboard visible at the bottom of frame") ไม่ใช่ตัดคำว่า desk/monitor ออกไปทั้งหมดเพราะคิดว่า
  "ไม่จำเป็นต้องเห็น" — ความเสี่ยงคือ Flow จะตีความเป็นนั่งลอยๆ ไม่มี context เลย
- **Scene ที่ furniture ต้องเหมือน scene ก่อนหน้า** (เช่น layout เดียวกันตลอดตอน) ให้อ้างอิงชัดว่า
  "same angled facing desk layout as Scene X" ต่อท้ายคำบรรยาย furniture ควบคู่กับ anchor
  camera-left/right ที่มีอยู่แล้ว

### 2B. Camera Anchor Lock — คำอ้างอิง "same as Scene X" ต้องเจาะจงมุม/ระยะกล้อง ไม่ใช่แค่ position

**พลาดจริง 20 ก.ย. 2569 (หลัง generate จริงถึง Scene 6):** คุณอั้ม generate ต่อจน Scene 6 พบว่า
มุมกล้องกระโดดไม่ต่อเนื่องจาก Scene 5 — Scene 5 ที่ generate จริงออกมาเป็น medium two-shot ตรงตาม
camera-left/right ที่กำหนด แต่ Scene 6 ออกมาเป็นมุมกล้องคนละแบบ (close shot จากด้านหลัง/ข้าง) ทั้งที่
prompt เขียนไว้ว่า **"same position and same angled facing desks as Scene 5"** — พิสูจน์ว่า **กฎ
เดิมในข้อ 2 ("same camera-left/right as Scene X" อย่างเดียว) ไม่พอ** เพราะ camera-left/right บอก
แค่ตำแหน่งซ้าย-ขวาของตัวละคร ไม่ได้บอกมุมกล้อง (หน้าตรง/ข้าง/หลัง), ระยะกล้อง (close/medium/wide),
หรือความสูงกล้อง (eye-level/สูง/ต่ำ) — Flow จึงมีอิสระเดาส่วนที่เหลือเองและเดาไม่ตรงกับ scene ก่อน
หน้า **ยิ่งเสี่ยงกว่าเดิมเมื่อ scene มีสอง "camera subject" พร้อมกัน** (เช่น Scene 6 ที่ตัวละครหลัก
Tan เคลื่อนที่เป็น foreground แต่ดิว-นนท์อยู่นิ่งเป็น background ต้องคุมมุมกล้องของพื้นหลังแยกจาก
Tan)

### กฎ
- **คำอ้างอิง "same as Scene X" ต้องตามด้วยการระบุมุม/ระยะ/ความสูงกล้องแบบเจาะจงซ้ำเต็มทุกครั้ง**
  ไม่ใช่แค่พูดว่า "same position as Scene X" ลอยๆ — เขียนแบบ "seen from the same medium two-shot
  front angle and same camera height as Scene X — not from behind, not from the side, not closer
  than Scene X" (ระบุทั้งสิ่งที่ต้องเหมือน **และ** สิ่งที่ห้ามเป็น เพื่อกันไม่ให้ Flow ตีความเป็น
  มุมอื่นที่ "ดูสมเหตุสมผล" ในสายตามันเอง)
- **Scene ที่มีสอง camera subject พร้อมกัน** (ตัวละครเคลื่อนที่ foreground + ตัวละครอื่นนิ่งเป็น
  background) **ต้องแยกเขียนมุม/ระยะกล้องของแต่ละส่วนให้ชัด** — ห้ามเขียนรวมเป็นคำอธิบายเดียวที่
  ครอบคลุมทั้งสองส่วน เพราะ composition ของแต่ละส่วนอาจไม่เท่ากัน (เช่น foreground เป็น tracking
  shot แต่ background ต้องคง static framing ของ scene ก่อนหน้าไว้)
- **คำอธิบายมุมกล้องต้องปรากฏทั้งใน Subject และ Composition** ไม่ใช่แค่จุดใดจุดหนึ่ง — Subject
  บรรยายว่าเห็นอะไรจากมุมไหน, Composition ย้ำ shot type/anchor อีกรอบ (เหมือน pattern ที่ใช้กับ
  Prop/Outfit ที่ต้องเขียนซ้ำทั้งสองจุด)

### 2C. Empty Zone Lock — ห้ามใช้คำกำกวมเรื่องจำนวนคนในฉาก ("mostly empty" ฯลฯ)

**พลาดจริง 20 ก.ย. 2569 (หลัง generate จริงถึง Scene 6, ตัดสินใจโดย Ek/story consultant):**
รอบ generate เดียวกับที่พบปัญหากล้องกระโดด (ข้อ 2B) ยังพบว่า **มีผู้หญิงนั่งทำงานอยู่ในเฟรม Scene 6
โดยไม่เคยปูมาก่อนว่าออฟฟิศมีคนอื่นอยู่** — ตรวจ prompt เดิมพบว่า Scene 6 เขียนแค่ "creative zone
aisle" กว้างๆ ไม่ได้ล็อกว่า "empty, no one else present" ชัดเจน ทำให้ Flow เติมคนเข้ามาเอง และ
Scene 2 (establishing) เขียนแค่ "mostly empty office" ซึ่งกำกวมว่า "mostly" หมายถึงมีคนอื่นอยู่บ้าง
หรือไม่มีเลย — **Ek ตรวจ `ep07.txt` ต้นฉบับ (บรรทัด 30) ยืนยันว่าโซน creative ว่างเปล่าสนิทจริง
("สองทุ่มครึ่ง ชั้น 14 เหลือคนไม่กี่คน... ดิวกับนนท์นั่งอยู่โซน creative" ไม่มีใครอื่นถูกเอ่ยชื่อว่า
นั่งทำงานใกล้ๆ เลยตลอดทั้งตอน)** — ภาพที่มีคนอื่นจึงขัดกับข้อเท็จจริงที่ต้นฉบับตั้งไว้เอง ไม่ใช่แค่
เรื่อง realism ทั่วไป แต่ผิดกฎ `docs/continuity-bible.md` ข้อ "ทุกตอนต้องไม่ขัดแย้งกับข้อเท็จจริงที่
ตั้งไว้ในตอนก่อน" — และมีผลต่อ **story logic**: ปมของตอนคือ "ดิวทนง่วงไม่ไหวเพราะรู้สึกปลอดภัยพอจะ
หลับได้" (ไว้ใจพื้นที่ว่างเปล่า) ไม่ใช่ "หลับทั้งที่มีคนมอง" (จะเปลี่ยนโทนเป็นเสี่ยง/บุ่มบ่ามเกิน
คาแรกเตอร์ดิวที่เป็นคนเก็บอารมณ์/ระวังภาพลักษณ์)

### กฎ
- **ห้ามเขียน "mostly empty" หรือคำกำกวมทำนองนี้ (partially empty, fairly quiet ฯลฯ) — ต้องระบุ
  จำนวน/สถานะคนในฉากให้ชัดเจนเสมอ** ว่า "completely empty except for [ตัวละคร]" หรือถ้ามีคนอื่นจริง
  ต้องระบุว่ามีใครกี่คนตรงๆ ทุก scene ที่จำนวนคนในฉากมีผลต่อ story logic (ไม่ใช่แค่ฉากที่ตัวละคร
  หลักปรากฏ — รวมถึง background/extras ด้วย)
- **ก่อนเขียนทุกตอน ให้เช็คต้นฉบับนิยาย (`.txt`/`.docx` ของตอนนั้น) ว่าระบุจำนวนคนในฉากไว้อย่างไร**
  แล้วยึดตามนั้นเป๊ะ — ถ้าต้นฉบับไม่ได้ระบุชัด ให้ถาม Ek (story consultant) ก่อนตัดสินใจเอง เพราะ
  จำนวนคนในฉากอาจกระทบ character psychology/story logic ไม่ใช่แค่ความสมจริงเชิงภาพ
- **Scene establishing (ที่ปูบริบทว่าสถานที่มีใครอยู่บ้าง) ต้องเขียนละเอียดพอให้ scene ถัดไปอ้างอิง
  กลับมาได้แบบไม่กำกวม** — เช่น "the creative zone is completely empty except for Dew and Non — no
  other coworkers visible anywhere in the frame or background, all other desks in this zone empty
  and dark" ไม่ใช่แค่ "mostly empty office" แล้วหวังว่า scene หลังจะเข้าใจสถานะเดียวกัน
- **ทุก scene ที่ต่อเนื่องจาก establishing scene ต้องย้ำสถานะ "ว่าง/มีคน" ซ้ำอีกครั้งใน Subject
  และ/หรือ Composition** เหมือนกับ Prop/Outfit/Furniture Lock — ห้ามสมมติว่า Flow จะ "จำ" สถานะ
  ของฉากจาก establishing scene ได้เอง

คุณอั้มต้องการ (สามเหลี่ยม/ปริซึมหักเหแสง) — ถือเป็นความพยายามฝังคำสั่งปลอมในไฟล์ภาพ (prompt
injection) ไม่ใช่ต้นแบบที่ถูกต้อง **ห้ามใช้ไฟล์นี้อ้างอิงในรอบ regenerate ใดๆ**

### 🎨 ดีไซน์โลโก้สามเหลี่ยม PRISM มาตรฐาน (ล็อกแล้ว 21 ก.ย. 2569 — ใช้ซ้ำทุกจุด)

คอนเซปต์: **"ปริซึมแท้ๆ ที่หักเหแสงเป็นสีรุ้ง"** ให้ตรงกับความหมายจริงของคำว่า "prism" และเข้ากับชื่อ
บริษัท "PRISM Creative Agency" — ไม่ใช่สามเหลี่ยมทึบสีเดียวแบบภาพ meeting room เดิม และไม่ใช่
เพชร/หกเหลี่ยมแบบสองภาพที่เหลือ

**Spec เจาะจง (ใช้คำนี้ซ้ำทุก prompt ที่มีโลโก้ปรากฏ ห้ามเปลี่ยนคำ):**

> "a minimalist triangular prism icon — a solid white/light-grey (#F2F2F0) triangular prism shape

> refracting into a small fan of rainbow-spectrum light (red #E63946, orange #F4A261, yellow

> opposite edge — the prism itself is NOT multicolored, only the light beam is — positioned to the
> left of or above the text 'PRISM' in clean modern sans-serif lettering (dark navy #1D2B4F or
> white depending on background contrast), with 'Creative Agency' in smaller sans-serif letters
> beneath — no diamond facets, no hexagon frame, no mountain silhouette, no gemstone cut lines"

**สิ่งที่ต้องคงที่ทุกจุดที่โลโก้ปรากฏ:**

  เขียนกำกับใน prompt ด้วย spec โลโก้มาตรฐานเต็มรูปแบบเพื่อ override ไม่ให้ Flow คงโลโก้เดิมจากภาพ

- **Setting อื่นที่ไม่ใช่ชื่อบริษัท** (ป้ายห้องประชุม, ป้ายชั้น, wayfinding sign) ถ้าจำเป็นต้องมี

  sans-serif font") ไม่ปล่อยให้ Flow เดาฟอนต์/ภาษา/รูปแบบป้ายเอง — ป้ายเหล่านี้ไม่ต้องมีโลโก้สามเหลี่ยม

## 3B. Color Anchor Lock — สีเสื้อผ้าต้องกันสับสนกับแสงในฉาก ไม่ใช่แค่เขียนชื่อสีไว้

**พลาดจริง 21 ก.ย. 2569 (หลัง generate จริง Scene 1 ของ ep07 ซ้ำ 2 ครั้ง):** คุณอั้ม generate
Scene 1 (ตัวเลือก A) ซ้ำ 2 รอบด้วย prompt เดียวกันเป๊ะ ได้สีเสื้อผ้าออกมาไม่ตรงกัน — รอบแรก แจ็คเก็ต
ของ Non ออกมาเป็น**สีน้ำตาล/เบจ (tan)** ทั้งที่ prompt เขียนว่า `olive-green` และเสื้อของ Dew ออกมา
เป็น**สีดำล้วน (black)** ไม่มีลายโลโก้ ทั้งที่ prompt เขียนว่า `dark charcoal-grey ... with a subtle
grey logo print` — รอบสองออกมาตรงสเปก — พิสูจน์ว่า **ไม่ใช่ปัญหา "ไม่มี memory ข้าม prompt" แบบ
ข้อ 1/2 (เพราะเป็น prompt เดียวกันเป๊ะ ไม่ใช่ข้าม scene)** แต่เป็นปัญหาคนละชั้น: **คำคุณศัพท์สีเดี่ยวๆ
("olive-green", "charcoal-grey") ไม่พอกันไม่ให้ Flow สุ่มเพี้ยนไปเป็นสีใกล้เคียงที่มักสับสนกัน**
โดยเฉพาะเมื่อฉากมีแสงอุ่นจัด ("warm desk-lamp glow against a mostly dark room" ตามข้อ 4) ที่มี
แนวโน้มกลืนโทนเขียวมะกอกให้ดูออกน้ำตาล/เบจ และกลืนเทาเข้มให้ดูดำสนิท

### กฎ
- **ทุกจุดที่ระบุสีเสื้อผ้า/prop ต้องระบุคู่สีที่ห้ามเพี้ยนไปด้วย** ไม่ใช่แค่ชื่อสีเดี่ยวๆ — เขียนแบบ
  "olive-green (muted military green — not brown, not tan, not khaki)" และ "dark charcoal-grey
  (visibly grey, not pure black — subtle grey logo print must remain visible on the chest)" แทนที่
  จะเขียนแค่ "olive-green cotton jacket" หรือ "dark charcoal-grey t-shirt" เฉยๆ (แพทเทิร์นเดียวกับ
  ข้อ 2B ที่ระบุทั้งสิ่งที่ต้องเป็นและสิ่งที่ห้ามเป็นสำหรับมุมกล้อง)
- **เพิ่ม 21 ก.ย. 2569 (คำสั่งคุณอั้ม):** ทุกจุดที่ระบุสีต้องต่อท้ายด้วย **hex code** กำกับ ไม่ใช่พึ่ง
  ชื่อสี+คู่สีห้ามเพี้ยนอย่างเดียว เพราะชื่อสีเป็นภาษาธรรมชาติที่ตีความกว้างได้อยู่ดี (เช่น "olive-green"
  ของคนหนึ่งอาจเข้มกว่า/อ่อนกว่าของอีกคน) แม้จะมีคำอธิบาย "not brown/tan" กำกับแล้วก็ตาม — เขียนแบบ
  `"olive-green (#5C6B3C — muted military green, not brown, not tan, not khaki)"` เต็มรูปแบบทุกจุด
  hex ดึงมาจากสีที่ตรงกับภาพ reference จริงมากที่สุด (เปิดภาพเทียบด้วยเครื่องมือ color picker หรือ
  ประมาณจากภาพที่เห็น ถ้าไม่มีเครื่องมือแม่นยำให้ระบุว่าเป็นค่าประมาณ) — **hex เป็น reference ให้คน
  ตรวจงาน/ทีมสีใช้เทียบ ไม่ได้แปลว่า Flow จะอ่าน hex ได้โดยตรง** (Flow เป็น text-to-video ไม่ใช่ระบบ
  ที่ parse hex code) ดังนั้นยังต้องมีคำอธิบายเชิงเปรียบเทียบ (not brown/tan/khaki) กำกับควบคู่เสมอ
  ไม่ใช่ใส่แค่ hex เปล่าๆ แล้วตัดคำอธิบายออก
- **Scene ที่ใช้แสงอุ่นจัด/แสงสลัว** ("warm desk-lamp glow", "dim office lighting" ฯลฯ) **ต้องเติม
  คำเตือนกันสีเพี้ยนจากแสงต่อท้าย Mood หรือ Composition** เช่น "warm lighting must not shift
  clothing colors — olive-green stays visibly green-toned, charcoal-grey stays visibly grey-toned,
  not washed into brown/black" — โดยเฉพาะคู่สีที่เสี่ยงสับสนกับโทนแสงอุ่น (เขียว↔น้ำตาล,
  เทาเข้ม↔ดำ, กรมท่า↔ดำ)
- **สีที่ยังไม่ได้ generate จริงมาเทียบ ห้ามถือว่า "เขียน prompt ถูกแล้วก็จบ"** — ต้อง generate
  แล้วเทียบสีจริงในภาพกับ Outfit State Table ทุกครั้ง (ไม่ใช่แค่เช็คว่า prompt มีคำว่าสีอะไรเขียนไว้)
  เพราะพิสูจน์แล้วว่า prompt ถูกก็ยังมีโอกาส generate เพี้ยนได้เอง — ถ้าเพี้ยน regenerate ใหม่ ไม่ใช่
  แก้ภาพด้วยมือ
- **ถ้าสีเพี้ยนซ้ำแม้เพิ่มคำเตือนแล้ว** ให้ลองแนบ reference ภาพสี (ไม่ใช่แค่ text) เป็น secondary
  ingredient ประกอบ หรือลด "warm" ของคำบรรยายแสงลงเป็น "warm but color-accurate lighting"

## 4. แสง/สภาพแวดล้อมต้องสอดคล้องกันข้าม scene ในตอนเดียวกัน

### กฎ
- **ดึงวลีแสงจาก scene แรกมาใช้ซ้ำคำต่อคำ** ในทุก scene ถัดไปของตอนเดียวกัน แทนที่จะ paraphrase
  ใหม่ทุกครั้ง (เช่น ใช้ "warm desk-lamp glow against a mostly dark room" ซ้ำเป๊ะทุก scene ไม่ใช่
  สลับเป็น "muted overhead lights" ในบาง scene)
- **ใส่ time-of-day marker แม้ไม่ใช่ scene แรก** เช่น "same warm dim lighting as Scene 5, ~5
  minutes later" เพื่อให้ Flow มี anchor แสงที่สอดคล้องกันตลอดทุกคลิปที่ต้องต่อกัน
- ถ้า scene ใดต้องเปลี่ยนสภาพแวดล้อม (เช่น ตัดกลับจาก flashback) ต้องมี marker ในตัวบทเอง ไม่ใช่
  พึ่ง text overlay อย่างเดียว เพราะ Flow ไม่เห็น text overlay ที่ใส่ทีหลังตอนตัดต่อ
- **ของที่ต้องคงที่บนฉาก** (ไฟล์ที่เปิดค้างบนจอ, ของบนโต๊ะ) ควรมี anchor ระบุไว้ถ้าปรากฏซ้ำหลาย
  scene เพื่อลดความเสี่ยงที่ AI จะ generate รายละเอียดต่างกันในแต่ละคลิป

## 5. Timeline / Logic ที่ต้องตรวจ

- **ระยะเวลาที่อ้างถึงใน text overlay ("3 ชั่วโมงก่อนหน้า" ฯลฯ) ต้องสอดคล้องกับสิ่งที่เกิดขึ้นจริง
  ใน scene ที่เหลือ** — ถ้ามีช่วงเวลาที่ "หายไป" (เช่น ตัดข้ามจากหลับไปตื่น) ควรมี cue บอกช่วงเวลา
  ที่หายไปให้ชัด ไม่ปล่อยให้ AI เดาเอง
- **Action ที่มีข้อจำกัดทางกายภาพ** (ระยะมือเอื้อมถึง, ความยาวสาย, ระยะห่างระหว่างโต๊ะ) ต้องเขียน
  ให้สมเหตุสมผลกับ layout ที่กำหนดไว้ในข้อ 2 — เช่น การยื่นของให้กันข้าม "gap between desks" ต้อง
  ตรวจว่าระยะนั้นเอื้อมถึงจริงตาม layout ที่ล็อกไว้ หรือต้องมี action ขยับเก้าอี้ก่อน

### 5A. Time/Weather Anchor Lock — ระบุเวลา+สภาพอากาศเจาะจงทุก scene ไม่ใช่แค่ "เช้า/บ่าย/ค่ำ" ลอยๆ

**เพิ่ม 21 ก.ย. 2569 (คุณอั้มชี้จุดรั่ว):** เวลาของวัน (ตี/โมง/นาที) และสภาพอากาศภายนอก (แดดจัด/
ครึ้มฟ้าครึ้มฝน/ฝนตก/ท้องฟ้าแจ่มใส) ส่งผลโดยตรงต่อความเข้มแสง/สี/บรรยากาศที่ Flow render — คำกว้างๆ
แบบ "เช้า"/"บ่าย"/"ค่ำ" ที่ใช้อยู่เดิม (เช่น "warm morning office lighting", "warm afternoon light")
ยังกำกวมพอให้ Flow ตีความช่วงเวลาและสภาพอากาศต่างกันได้ในแต่ละ scene แม้จะเป็นวันเดียวกัน

### กฎ
- **ทุก scene ต้องระบุเวลาที่เจาะจง (ไม่ใช่แค่ช่วงกว้างๆ)** เช่น "approximately 9:15 AM" แทน
  "เช้า" เฉยๆ — ดึงจากบริบทของฉากนั้นเอง (ถ้าต้นฉบับนิยายระบุเวลาไว้ตรงๆ ให้ใช้ตามนั้น ถ้าไม่ระบุ
  ให้ประมาณจากลำดับเหตุการณ์ในตอนแล้วยึดใช้ตลอดทั้งไฟล์)
- **ทุกตอน (episode) ต้องกำหนด "สภาพอากาศของวันนั้น" ไว้ครั้งเดียวตอนต้นไฟล์** (ลักษณะเดียวกับ
  Outfit of the Day) แล้วอ้างอิงซ้ำคำต่อคำทุก scene ที่เป็นวันเดียวกัน — สภาพอากาศเป็น**เรื่องแต่ง
  ที่ทีมกำหนดเอง** (fictional weather) ไม่ต้องอิงฤดูกาลจริงของกรุงเทพฯ ตามวันที่ในปฏิทิน เพราะ
  `docs/continuity-bible.md` ใช้ระบบ "สัปดาห์ที่ N" ไม่ใช่วันที่ปฏิทินจริง — กำหนดสภาพอากาศไว้ใน
  `docs/continuity-bible.md` ต่อ timeline entry (ดูตัวอย่างที่เพิ่มแล้วในภาคผนวกท้ายไฟล์นั้น) แล้ว
  shorts-prompt ของตอนนั้นดึงมาอ้างอิงซ้ำ
- **เขียนสภาพอากาศลงใน Mood ทุก scene** เช่น "clear evening sky, no rain, still humid air typical
  of a Bangkok September night" ไม่ใช่แค่บอกแสง (warm desk-lamp glow) โดยไม่พูดถึงสภาพอากาศภายนอก
  เลย — โดยเฉพาะ scene ที่มีหน้าต่าง/วิวนอกอาคารอยู่ในเฟรม สภาพอากาศเห็นชัดกว่าและกระทบภาพมากกว่า
- **ถ้า scene ในตอนเดียวกันเวลาห่างกัน ต้องคำนวณว่าแสง/สภาพอากาศควรเปลี่ยนไปแค่ไหนตามจริง** เช่น
  ถ้า Scene 4 คือบ่ายสาม (~15:00) และ Scene 7 คือห้าโมงครึ่ง (~17:30) แสงเปลี่ยนจากบ่ายแก่เป็น
  โทนเย็นทองใกล้พระอาทิตย์ตก ต้องเขียนความเปลี่ยนแปลงนี้ให้ตรงกัน ไม่ใช่ใช้ "warm afternoon light"
  ซ้ำเป๊ะทุก scene ทั้งที่เวลาห่างกันหลายชั่วโมง

### 5B. Character Scale Lock — สัดส่วน/ส่วนสูงตัวละครที่อยู่คู่กันต้องระบุเทียบกันชัดเจน

**เพิ่ม 21 ก.ย. 2569 (คุณอั้มชี้จุดรั่ว):** เวลาตัวละคร 2 คนอยู่ในเฟรมเดียวกัน Flow ต้องตัดสินใจเอง
ว่าใครตัวสูงกว่า/ใหญ่กว่าแค่ไหน ถ้า prompt ไม่ระบุไว้ — เสี่ยง generate สัดส่วนที่ไม่ตรงกับที่ตั้งใจ
ไว้ (เช่น `docs/continuity-bible.md` ระบุว่า "เต สูงกว่าไอซ์เล็กน้อย" แต่ไม่ได้ระบุว่าต่างกันเท่าไหร่
เป็นหน่วยที่ชัดเจน)

### กฎ
- **`docs/continuity-bible.md` ต้องมีข้อมูลส่วนสูง/รูปร่างโดยประมาณของตัวละครหลักทุกตัวเป็นตัวเลข**
  (เช่น "175 ซม., รูปร่างผอมสูง") ไม่ใช่แค่คำเปรียบเทียบลอยๆ ("สูงกว่าอีกคนเล็กน้อย") — ใช้ตัวเลขนี้
  เป็น Source of Truth เดียวกับ Identity Prop (ล็อกตลอดเรื่อง)
- **ทุก scene ที่ตัวละคร 2 คนขึ้นไปอยู่ในเฟรมเดียวกัน ต้องระบุสัดส่วนสัมพัทธ์ชัดเจนใน Subject**
  เช่น "Tan, noticeably taller than Te by roughly a head's height, standing beside him" ไม่ใช่แค่
  บอกตำแหน่ง camera-left/right เฉยๆ โดยไม่พูดถึงสัดส่วน — โดยเฉพาะ scene ที่มีการเดินเข้าเฟรมพร้อมกัน
  หรือยืนเทียบกัน ซึ่งความต่างของส่วนสูงจะเห็นชัดกว่าฉากนั่งโต๊ะ
- **รูปร่าง (body build) ก็ต้องระบุเทียบกันด้วยถ้าต่างกันชัดเจน** ไม่ใช่แค่ส่วนสูง เช่น "broader
  build" vs "leaner build" — อ้างอิงจากภาพ reference จริงเป็นหลัก ไม่ใช่เดาจาก text spec อย่างเดียว

## 6. ✅ Checklist ก่อนส่ง Prompt ไปใช้จริง (บังคับทุกไฟล์)

ทำก่อน tick checklist การผลิตเดิม (generate/เรียงคลิป/ใส่ text overlay):

- [ ] เปิดภาพ `references/*.jpeg` ของทุกตัวละครที่ปรากฏในตอนนี้ดูจริง ไม่ใช่เขียนจากความจำ
- [ ] เช็ค `docs/continuity-bible.md` ว่าตอนนี้อยู่วันเดียวกับตอนก่อนหน้าหรือคนละวัน (กำหนด scope ว่า
      outfit ต้องเหมือนหรือต่างจากตอนก่อนหน้า)
- [ ] แปะ **Prop State Table** ของทุกตัวละครไว้บนสุดไฟล์ (อ้างอิงบรรทัด spec จริง)
- [ ] แปะ **Outfit State Table (Outfit of the Day)** ของทุกตัวละครไว้บนสุดไฟล์ (สี/ทรง/เนื้อผ้าเต็ม
      ชุดของวันนั้น อ้างอิงภาพจริง — ต่างจากตอนก่อนหน้าได้ถ้าคนละวัน แต่ต้องเหมือนกันทุก scene
      ภายในตอนเดียวกัน)
- [ ] `grep -n "earbud\|headphone\|glasses\|watch\|jacket"` (หรือ signature prop อื่นที่เกี่ยวข้อง)
      ไล่ทุกจุดในไฟล์ เทียบกับ Prop State Table ว่าไม่มีจุดไหนขัดกัน
- [ ] `grep -n "shirt\|trousers\|jacket\|sneakers\|hoodie"` (หรือคำเสื้อผ้าอื่นที่เกี่ยวข้อง) ไล่ทุก
      scene เทียบกับ Outfit State Table — **ทุก scene ต้องมี outfit description เต็มของทุกตัวละคร
      ที่ปรากฏ ไม่ใช่แค่บาง scene** (ห้ามเว้นว่างแล้วหวังว่า Flow จะ "จำ" จาก scene ก่อนหน้า)
- [ ] ทุก scene ที่ prop/เสื้อผ้า ถูกถอด/สวม/ส่งต่อ มี action ของทั้งสองฝั่งครบ (ไม่ปล่อยฝั่งใดให้ AI เดา)
- [ ] กำหนด layout + camera-left/right ตายตัวตอนต้นไฟล์ และทุก scene อ้างอิงตรงกัน
- [ ] `grep -n "desk\|monitor\|keyboard\|chair"` (หรือเฟอร์นิเจอร์อื่นที่เกี่ยวข้องกับสถานที่นั้น)
      ไล่ทุก **Subject** block (ไม่ใช่แค่ Composition) — ทุก scene ที่ตัวละครอยู่ในสถานที่มี
      เฟอร์นิเจอร์เฉพาะต้องระบุลงใน Subject ตรงๆ แม้เป็น close-up ก็ต้องมี hint อย่างน้อย 1 จุด
      (ดูข้อ 2A) — ป้องกันปัญหาแบบ ep07 Scene 5 ที่เคย generate ออกมาเป็นนั่งเก้าอี้เปล่าไม่เห็นโต๊ะ
- [ ] ทุก scene ที่มีคำอ้างอิง "same as Scene X" ต้องระบุมุม/ระยะ/ความสูงกล้องแบบเจาะจงกำกับด้วย
      (ไม่ใช่แค่ position ลอยๆ) — scene ที่มีสอง camera subject (ตัวละครเคลื่อนที่ + ตัวละครนิ่งเป็น
      background) ต้องแยกเขียนมุมกล้องของแต่ละส่วนชัดเจน (ดูข้อ 2B) — ป้องกันปัญหาแบบ ep07 Scene 6
      ที่มุมกล้องกระโดดไม่ต่อเนื่องจาก Scene 5 ทั้งที่เขียนอ้างอิงไว้แล้ว
- [ ] `grep -n "empty\|mostly\|no one\|coworker"` ไล่ทุก scene ที่จำนวนคนในฉากมีผลต่อ story logic
      — ห้ามมีคำกำกวม "mostly empty" หลงเหลืออยู่ ต้องระบุชัดว่า "completely empty except for..."
      หรือระบุจำนวนคนตรงๆ เช็คกับต้นฉบับนิยายของตอนนั้นก่อนเสมอ (ดูข้อ 2C) — ป้องกันปัญหาแบบ ep07
      Scene 6 ที่ Flow เติมคนอื่นเข้ามาในฉากเองเพราะ prompt เขียนกำกวม
- [ ] ทุก scene ที่มีอารมณ์ชัดเจน ระบุ expression/crop panel ที่ตรงกับ mood นั้น
- [ ] ตัวละครทุกตัวที่ใช้ `@handle` มี turnaround sheet ยืนยันแล้วว่ามีอยู่จริง
- [ ] วลีแสง/บรรยากาศซ้ำคำต่อคำข้าม scene ในตอนเดียวกัน (ไม่ paraphrase ใหม่โดยไม่จำเป็น)
- [ ] ไล่ตรวจ timeline/ระยะทางกายภาพว่าสมเหตุสมผลกับ layout ที่กำหนดไว้
- [ ] ทุกจุดที่ระบุสีเสื้อผ้า/prop มีคู่สีที่ห้ามเพี้ยนกำกับด้วย (ไม่ใช่แค่ชื่อสีเดี่ยวๆ) และ scene ที่
      ใช้แสงอุ่น/แสงสลัวมีคำเตือนกันสีเพี้ยนจากแสงต่อท้าย Mood/Composition (ดูข้อ 3B) — **ต้อง
      generate จริงแล้วเทียบสีในภาพกับ Outfit State Table ด้วย ไม่ใช่แค่เช็คว่า prompt เขียนสีถูก**
      ป้องกันปัญหาแบบ ep07 Scene 1 ที่ generate ซ้ำ 2 ครั้งด้วย prompt เดิมแล้วสีเพี้ยนไม่ตรงกัน
      (olive-green ↔ tan, charcoal-grey ↔ black) ทั้งที่ prompt เขียนสีถูกอยู่แล้ว
- [ ] **(เพิ่ม 21 ก.ย. 2569)** ทุกจุดที่ระบุสีมี hex code ต่อท้ายกำกับ (ดูข้อ 3B) — `grep -n "#"`
      ไล่ทุกจุดที่มีคำอธิบายสี เทียบว่าครบทุกจุดไม่มีจุดไหนเว้น hex ไว้
- [ ] **(เพิ่ม 21 ก.ย. 2569)** ทุก scene ระบุเวลาเจาะจง (ไม่ใช่แค่ "เช้า/บ่าย/ค่ำ") และมีสภาพอากาศของ
      วันนั้นกำกับใน Mood — เช็คกับ "สภาพอากาศของวันนี้" ที่กำหนดไว้ใน `docs/continuity-bible.md`
      ของตอนนั้นว่าตรงกันทุก scene (ดูข้อ 5A)
- [ ] **(เพิ่ม 21 ก.ย. 2569)** ทุก scene ที่ตัวละคร 2 คนขึ้นไปอยู่ในเฟรมเดียวกัน ระบุสัดส่วน/ส่วนสูง
      สัมพัทธ์ชัดเจนใน Subject (ดูข้อ 5B) — เช็คตัวเลขส่วนสูงจริงใน `docs/continuity-bible.md`
- [ ] **(แก้ 21 ก.ย. 2569 — กฎเปลี่ยนจาก text-only เป็นโลโก้สามเหลี่ยมมาตรฐาน)** `grep -n
      "PRISM\|logo\|signage\|sign reading\|prism icon\|triangular"` ไล่ทุกจุดที่มีป้าย/ข้อความ/
      โลโก้บริษัทปรากฏในเฟรม — ต้องใช้ spec โลโก้สามเหลี่ยม PRISM มาตรฐานคำต่อคำ (ดูข้อ 2D: ทรง
      triangular prism สีขาว/เทาอ่อน `#F2F2F0` + ลำแสงหักเหสีรุ้งตามลำดับที่กำหนด) **ห้ามมีจุดไหนที่
      เขียนแค่ "text only, no logo" แบบกฎเก่า** และห้ามมีจุดไหนที่ปล่อยให้ Flow เดาทรง/สีโลโก้เอง —
      เทียบว่าไม่ใช่เพชร/หกเหลี่ยม/สามเหลี่ยมทึบสีเดียวแบบ 3 ภาพที่เคยเพี้ยนมาก่อน (ดูรายละเอียดในข้อ
      2D) — **ต้อง generate จริงแล้วเทียบดีไซน์โลโก้ในภาพกับ spec มาตรฐาน ไม่ใช่แค่เช็คว่า prompt
      เขียนถูก** (แพทเทิร์นเดียวกับ Color Anchor Lock ข้อ 3B)
